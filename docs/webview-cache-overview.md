# WebView in-app: что качается, как кэшируется, откуда берётся — полная выкладка

Валидировано `curl`-ом по реальным URL (заголовки/размеры сняты 2026-07-01, endpoint `Mpush-test.WebView`).
Числа по показу — из профилирования на iPhone 17 Pro (см. `webview-show-profile.md`).

## 1. Что качается при показе (инвентарь, провалидировано)

| Ресурс | URL (домен) | Размер | Что внутри |
|---|---|---|---|
| **index.html** («popup» document) | `mobile-static.mindbox.ru/stable/inapps/webview/content/index.html` | 1.5 КБ | Бутстрап-страница: подключает main.js и tracker.js; путь трекера из `window.__env_vars.TRACKER_PATH` |
| **main.js** | `mobile-static.mindbox.ru/.../content/main.js?v=1.0.29` | 6.2 КБ | Загрузчик/склейка SDK-моста и рантайма |
| **tracker.js** | `api.mindbox.ru/scripts/v1/tracker.js?v=1.0.29` | 94 КБ | Web-трекер Mindbox (общий рантайм) |
| **byendpoint.js** | `web-static.mindbox.ru/js/byendpoint/<endpoint>.js?_=<5-мин>` | **826 КБ** | **Все формы эндпоинта (130 formId) + их статичные картинки** |
| **fonts css** | `fonts.googleapis.com/css2?...Source+Sans+3...` | 5.2 КБ | CSS шрифтов |
| **картинки формы** | `personalization-web(.g/-stable).mindbox.ru/user-media/<sha256>.png\|jpg\|webp` | 0.5–2.2 МБ каждая | Изображения конкретной формы (content-addressed) |

**Итого на один показ стирашки** (2 картинки): ≈ **3.8 МБ**, из которых картинки ~2.9 МБ (76%), byendpoint 826 КБ (21%), остальное <3%.

Общий рантайм (index/main/tracker/byendpoint/fonts) **один на все показы эндпоинта**; на каждый показ добавляются только **картинки конкретной формы**.

## 2. Как кэшируется (по заголовкам, провалидировано)

Кэширует нативный **WebKit NetworkCache** (не `NSURLCache`), если `websiteDataStore = .default()`/изолированный (персистентный). Сейчас в SDK `.nonPersistent()` → **кэш выключен**.

| Ресурс | `Cache-Control` | Срок свежести | ETag | Кэшируем |
|---|---|---|---|---|
| index.html | `public, max-age=600` | 10 мин | ✅ | ⚠️ но SDK тянет его **заново каждый показ** (эфемерная сессия, no-cache) |
| main.js | `public, max-age=600` | 10 мин | ✅ | ✅ |
| tracker.js | `public, max-age=86400` | 1 день | ✅ (weak) | ✅ |
| byendpoint.js | `public, max-age=600` | 10 мин | ✅ | ✅ (в пределах 5-мин бакета — см. §3) |
| fonts css | `private, max-age=86400` | 1 день | ✅ | ✅ (`private` = только приватный кэш, WebKit кэширует) |
| картинки | `max-age=604800`, immutable-подобно | 7 дней | ✅ | ✅ |

Замерено: с персистентным кэшем byendpoint отдаётся из кэша за **0–3 мс** вместо ~322–345 мс скачивания; картинки на повторе — из кэша.

## 3. Что будет, если файл закэширован, а на сервере новая версия

Механизм WebKit: в пределах `max-age` — отдаёт из кэша **без сети**; после — **условный запрос по ETag** (`If-None-Match` → `304` «оставить кэш» / `200` «заменить»). Проверено: все 6 ресурсов отвечают `304` на условный запрос. Плюс URL'ы версионируются, поэтому «новая версия» обычно = **новый URL**.

| Файл | Как версионируется | Если закэширован, а вышла новая версия |
|---|---|---|
| **index.html** | `max-age=600`+ETag; **SDK и так тянет заново** каждый показ | Всегда свежий → диктует актуальные версии остального |
| **tracker.js** `?v=1.0.29` | версия в URL (из index.html) | Бамп версии → index.html меняет `?v=` → **новый URL → свежий**. Тот же URL, но контент сменился → из кэша до 1 дня, потом ETag-ревалидация |
| **main.js** `?v=1.0.29` | версия в URL | То же; иначе ≤10 мин, потом ревалидация |
| **byendpoint.js** `?_=floor(now/5м)` | кэш-бастинг каждые 5 мин | **Новый URL каждые 5 мин → максимум 5 мин staleness**, дальше свежий сам |
| **fonts css** | `max-age=86400`+ETag | ≤1 день, потом ревалидация; меняется редко |
| **картинки** `…/<sha256>.png` | **content-addressed (immutable)** | **Никогда не устаревают**: новый контент = новый хэш = новый URL |

**Ключевая безопасность:** index.html **всегда свежий** (SDK тянет без кэша) и диктует версии (`?v=`) всего остального. → Закэшированная **старая версия никогда не отдаётся показу**: при бампе версии WebView запросит новый URL, старая запись игнорируется. Максимум устаревания без бампа = `max-age` (byendpoint 5 мин, main 10 мин, tracker/шрифты 1 день, картинки — никогда).

## 4. Откуда берётся инфа о каждом попапе

Два слоя:

| Слой | Источник | Что содержит |
|---|---|---|
| **SDK-конфиг** (нативный) | `api.mindbox.ru/mobile/byendpoint/<endpoint>.json` ([InAppConfigurationAPI.swift:89](../Mindbox/InAppMessages/Configuration/API/InAppConfigurationAPI.swift#L89)) | Список всех ин-аппов эндпоинта: `id`, `formId`, `targeting`, `frequency`, `baseUrl`, `contentUrl`. Решает **какие** попапы и **когда** |
| **Web-рантайм** | `web-static.mindbox.ru/js/byendpoint/<endpoint>.js` | **Все 130 форм** эндпоинта: разметка + статичные картинки. Решает **как** выглядит |
| **Персонализация** (рантайм) | api Mindbox (рекомендации/продукты) | Для рекомендательных форм — контент/картинки **по конкретному юзеру** |

**Достаточно ли одного эндпоинта?** Да — и SDK-конфиг, и web-byendpoint содержат **ВСЕ попапы эндпоинта разом** (один запрос каждого). На каждый показ добавляются только картинки конкретной формы.

## 5. Можно ли заранее подкачать картинки в кэш

Зависит от типа формы:

| Тип формы | Где картинки | Заранее подкачать? |
|---|---|---|
| **Статичные** (стирашка, онбординг) | **URL зашиты в byendpoint.js** (нашёл там точь-в-точь картинки стирашки: `…/800/3bfd709c…png`, `…/800/9d237fc2…png`), content-addressed, кэш 7 дней | ✅ **Да** — URL известны из byendpoint → можно распарсить и префетчить, или отрендерить форму скрыто |
| **Рекомендательные / персональные** | тянутся рантаймом по юзеру (в byendpoint только рекоменд-блок, не сами картинки) | ❌ **Нет** — URL рождается при рендере под юзера, заранее неизвестен |

Т.е. «картинки каждый раз новые» — верно для **рекомендательных** форм. Для статичных картинки стабильны и кэшируемы наперёд.

## 6. WKWebsiteDataStore — лимиты, поведение, хранение (с цитатами)

Пометки: **[Docs]** — Apple developer docs / заголовок WebKit; **[Impl]** — из исходников WebKit (верно, но деталь реализации, может меняться между версиями iOS).

### Варианты стора

| Вариант | Переживает перезапуск | Где | Прим. |
|---|---|---|---|
| `.default()` | **Да**, «stores data persistently to disk… retain state between browsing sessions» | app container, диск | дефолт конфига **[Docs]** |
| `.nonPersistent()` | **Нет**, «stores website data in memory, doesn't write to disk» (private browsing) | память | сейчас в SDK **[Docs]** |
| `init(forIdentifier:)` iOS 17+ | **Да** | отдельная папка на `<UUID>` | несколько персист-сторов; надо помнить UUID **[Docs]** |

Типы данных (`WKWebsiteDataType`): DiskCache, MemoryCache, Cookies, LocalStorage, SessionStorage, IndexedDB, WebSQL, OfflineWebApplicationCache **[Docs]**. Диск-путь сетевого кэша: `Library/Caches/WebKit/NetworkCache` **[Impl]**.

### Размер и лимиты

- WebKit использует **свой NetworkCache**, не `NSURLCache` **[Impl]**.
- **Ёмкость выводится из свободного места на диске**, не фиксирована; выбирается по `CacheModel` **[Impl]**:

| Свободно на диске | PrimaryWebBrowser (Safari) | DocumentBrowser | DocumentViewer |
|---|---|---|---|
| ≥16 ГБ | 1 ГБ | 75 МБ | 0 |
| ≥8 ГБ | 500 МБ | 40 МБ | 0 |
| ≥4 ГБ | 250 МБ | 30 МБ | 0 |
| ≥2 ГБ | 200 МБ | 20 МБ | 0 |
| ≥1 ГБ | 150 МБ | 20 МБ | 0 |
| <1 ГБ | 100 МБ | 20 МБ | 0 |

Приложение со встроенным WKWebView обычно попадает в диапазон DocumentViewer/DocumentBrowser (не 1 ГБ Safari); **точный дефолтный CacheModel для голого WKWebView примарным источником не зафиксирован** — считать «какой тир» недокументированным. **[Impl]**
- **Публичного API задать байтовую ёмкость НЕТ** (нет аналога `URLCache.diskCapacity` для `WKWebsiteDataStore`) **[Impl / подтверждено отсутствием в docs]**.

### Вытеснение (LRU?)

- **Не строгий LRU — вероятностное вытеснение по «worth».** При превышении ёмкости `shrinkIfNeeded()` → `shrink()`; у каждой записи вероятность удаления `computeRecordWorth = accessAge/age` (чаще/недавно читали → выше «ценность», ниже шанс удаления), макс. вероятность 0.33; общие blob-тела защищены. Триггер — **давление по ёмкости** **[Impl]**.
- **HTTP-заголовки управляют свежестью/ревалидацией** (`max-age`, `ETag`, `immutable`), но **не защищают запись от вытеснения по ёмкости** — свежую запись всё равно могут выкинуть **[Impl]**.
- **Офлайн — best-effort, не гарантирован.** Нет публичного «pin to cache»; запись могут вытеснить/почистить системой **[Docs/Impl]**.

### Управление размером — публичное API

- `fetchDataRecords(ofTypes:)` — список записей по origin (**без байт**) **[Docs]**.
- `removeData(ofTypes:for:)` / `removeData(ofTypes:modifiedSince:)` — чистить по origin / по дате (`.distantPast` = всё) **[Docs]**.
- iOS 17+: `remove(forIdentifier:)` — снести весь изолированный стор; `fetchAllDataStoreIdentifiers` **[Docs]**.
- **Текущий размер кэша в байтах публично НЕ прочитать** (`WKWebsiteDataRecord` не отдаёт байты; `dataSize` — SPI). → Свою политику «посчитать байты и подрезать до N» **на публичном API не сделать**; можно только удалять по origin/дате или сносить весь стор **[Docs]**.

**Вывод по стору:** переживает перезапуск (`.default()`/`forIdentifier`); ёмкость системная (десятки–сотни МБ по свободному месту); нельзя задать байтовый лимит и нельзя прочитать размер; вытеснение — LRU-подобное вероятностное; офлайн не гарантирован. Управление — только `removeData` (по дате/origin) или снос изолированного стора.

Источники: developer.apple.com/documentation/webkit/wkwebsitedatastore (+ `/default()`, `/nonpersistent()`, `/init(foridentifier:)`, `/ispersistent`, webkit-constants, wkwebsitedatarecord); webkit.org/blog/14423 (profiles API); WebKit source — `WKWebsiteDataStore.h`, `NetworkCache.cpp`, `NetworkCacheStorage.cpp`, `Shared/CacheModel.cpp`.

## 7. Что это значит для нашего cacher'а

- Кэш переживает перезапуск (`.default()`) — да; для приватности лучше iOS 17+ изолированный `forIdentifier`.
- Нельзя задать байтовый лимит/прочитать размер → бюджет держим политикой `removeData(ofTypes:modifiedSince:)` (по дате) или сносом изолированного стора; полагаться на «всегда в кэше» нельзя (best-effort).
- Cacher должен грузить **настоящий index.html** (он всегда актуален и диктует `?v=`), а не хардкодить версии — иначе после бампа версии cacher греет неактуальное (безопасно, но бесполезно).
- byendpoint кэшируем в пределах 5-мин бакета; кэш-бастинг воспроизводим (`floor(now/5м)`).
- Статичные картинки форм префетчиваемы (URL в byendpoint); рекомендательные — нет.
