# WebView-инапп: ускорение показа — решение и рекомендация для команды

> Ключевая правка: `websiteDataStore` `.nonPersistent()` → `.default()` (+ прогрев/reuse + cacher).
> Прототип провалидирован на ветке `prototype/webview-cache-profiling` (iPhone 17 Pro, два инаппа:
> стирашка ~3 МБ, онбординг). Этот документ — сводка для принятия решения; технические детали и сырые
> замеры — в приложениях внизу.

## TL;DR

Холодный показ WebView-инаппа сейчас **~2.3–3.4 с**. Причина складывается из трёх частей: (1) кэш
WebView в SDK **выключен** (`.nonPersistent()`) — всё качается заново каждый показ; (2) **~530 мс** на
спин-ап web-content процесса WebKit на каждый показ; (3) картинки формы (~2.9 МБ) качаются по сети.

Три независимых рычага, все на стороне SDK (без бэка/фронта):

1. **Персистентный кэш** (`.default()` / iOS 17+ изолированный стор) — повторный показ **~3–4× быстрее**.
2. **Прогрев + переиспользование** одного тёплого `WKWebView` — снимает ~345 мс с каждого показа.
3. **Cacher** — на прогреве грузим страничку, тянущую общий рантайм (tracker/main/byendpoint) в кэш →
   первый показ уже не платит за них.

**Стек вместе: полный показ ~2.3–3.4 с → ~0.3–0.4 с (≈7–9×)**; navStart ~620→~50 мс (переиспользованный
инстанс), byendpoint из кэша ~345→~1 мс. Свежий прогон двух инаппов подряд — в разделе «Замеренный эффект».

**Рекомендация:** шипить фазами — **Фаза 1** (кэш + reuse, чистый SDK, даёт основной выигрыш) →
**Фаза 2** (cacher) → **Фаза 3** (опц. серверный cacher + префетч картинок). Что нужно от команды —
в разделе «Что решаем».

## Что решаем

1. **Идём ли в персистентный кэш?** — главный рычаг. `.default()` персистит не только кэш, но и
   cookies/localStorage → нужен разбор приватности (что именно пишется, надо ли изолировать).
2. **Стор:** `.default()` (просто) vs iOS 17+ изолированный `WKWebsiteDataStore(forIdentifier:)`
   (чище по приватности; на iOS <17 — фоллбэк на `.default()`).
3. **Прогрев/reuse:** держать ли один живой `WKWebView` всю сессию (память — один инстанс).
4. **Cacher:** хардкод-страничка в SDK vs серверный `cacher.html`. Серверный нужен **только** для
   префетча статичных картинок форм; для Фаз 1–2 бэк не трогаем — прогрев грузит существующий
   `index.html` без formId (рантайм сам тянет актуальные версии, форма не рендерится).
5. **byendpoint-кэш:** оставить как есть (кэшируется в пределах 5-мин окна, `?_=floor(now/5мин)`) или
   попросить бэк отдать стабильный URL (тогда кэшируется всегда).
6. **Android:** включить кэш там же — гипотеза `LOAD_NO_CACHE` → `LOAD_DEFAULT` (`WebViewAndroid.kt`),
   не проверяли (окружения не было).

## Проблема — где уходит время

Медианы, стирашка, «как сейчас» (`.nonPersistent()` + новый WebView каждый показ), от `viewDidLoad`:

| Шаг | Что происходит | мс |
|---|---|--:|
| создание `WKWebView` | аллокация | ~47 |
| фетч бутстрап-HTML | сеть (ephemeral, no-cache) | ~40 |
| **спин-ап web-процесса** | первый `loadHTMLString` | **~530** |
| загрузка документа + скриптов |  | ~660 |
| **скачивание картинок ~2.9 МБ** | по сети | **~2160** |
| **итого «видно всё»** |  | **~3440** |

Отсюда три рычага: кэш убирает повторное скачивание, прогрев/reuse убирает спин-ап + создание, cacher
убирает первую загрузку рантайма.

## Решение — три рычага

| Рычаг | Что делает | Где в коде (прототип) | Эффект |
|---|---|---|---|
| **1. Персистентный кэш** | `websiteDataStore` `.nonPersistent()` → `.default()`; ресурсы кэшируются по заголовкам CDN, переживают перезапуск | `MindboxWebViewFacade.init` (флаг `-MBWVPersistentStore`) | повторный показ ~3–4× |
| **2. Прогрев + reuse** | один тёплый `WKWebView` на старте in-app подсистемы; **одалживается** каждому показу, на закрытии **скрывается, не уничтожается** (borrow-not-consume) | `WebViewShowProfiler.prewarmIfRequested()` из `InAppCoreManager.start()`; `borrowWarmWebView()` (флаг `-MBWVReuseInstance`) | −345 мс/показ; №2/№3 ещё быстрее |
| **3. Cacher** | локальная страничка тянет tracker+main+byendpoint+шрифты в кэш на прогреве | `WebViewShowProfiler.cacherHTML` (хардкод HTML-строкой, `loadHTMLString`) | первый показ не платит за рантайм; byendpoint 345→3 мс |

Профайлер (`WebViewShowProfiler`) и launch-флаги — **выкидные, измерительные**; в проде удаляются.
Мост сделан идемпотентным (`MindboxWebBridge.init`: `removeScriptMessageHandler` перед `add`), чтобы
reuse не дублировал хэндлер.

## Замеренный эффект

**Что весит на один показ** (стирашка, провалидировано `curl`; полная опись — overview §1):

| Ресурс | Вес | Кэш |
|---|--:|---|
| картинки формы (стирашка — 2 шт) | ~2.9 МБ | ✅ 7 дней |
| byendpoint.js (все формы эндпоинта) | 826 КБ | ✅ в 5-мин окне |
| tracker.js | 94 КБ | ✅ 1 день |
| main.js + fonts + index.html | ~13 КБ | ✅ |
| **итого показ** | **~3.8 МБ** | — |

Общий рантайм (byendpoint+tracker+main+fonts+index ≈ **0.93 МБ**) — один на все показы эндпоинта;
на каждый показ добавляются только картинки формы (~76% веса). Кэш убирает повторное скачивание того и
другого; на повторе byendpoint отдаётся за 0–3 мс вместо ~322–345 мс, картинки — из кэша.

### Два инаппа подряд в одной сессии (свежий прогон)

Медианы, N=6 (стек) / N=4 (как сейчас). Два показа в **одной сессии**: №1 стирашка + №2 онбординг (оба по
операции `APIMethodForReleaseExampleIos`). «Видно всё» = мс от `viewDidLoad`.

| Показ | как сейчас (cold, новый WebView) | стек (кэш + reuse) | ускорение |
|---|--:|--:|--:|
| **№1 стирашка** (2 карт., ~2.9 МБ) | 2976 | **396** | ~7.5× |
| **№2 онбординг** (3 карт.) | 2440 | **266** | ~9.2× |

navStart (создание + спин-ап), тот же прогон:

| Показ | cold | стек |
|---|--:|--:|
| №1 стирашка | 666 | 254 |
| №2 онбординг | 640 | **52** |

- **Показ №2 в стеке быстрее показа №1** (266 vs 396 мс), хотя онбординг тяжелее (3 картинки против 2) —
  переиспользованный инстанс уже показывал контент: navStart **52 vs 254 мс**.
- byendpoint в стеке — из кэша на обоих показах (`byendpointDur` 0–1 мс).
- **Каждый следующий показ в сессии остаётся быстрым → per-inapp прогрузка не нужна.**

### Разложение по рычагам

Сколько даёт каждый рычаг по отдельности («видно всё», медиана мс от `viewDidLoad`). Отдельный, более
ранний прогон — абсолютные мс между сессиями симулятора гуляют (сеть), сравнивать **внутри** таблицы;
паттерн тот же.

| Инапп | вес картинок | как сейчас | + только кэш | + только reuse | **кэш + reuse** | ускорение |
|---|--:|--:|--:|--:|--:|--:|
| **Стирашка** | ~2.9 МБ | 3440 | 800 | 2730 | **407** | **~8.5×** |
| **Онбординг** | легче (3 карт.) | 2267 | 793 | 1994 | **402** | **~5.6×** |

navStart (создание + спин-ап) — чистый нативный кост до загрузки контента; **от кэша не зависит** и
почти одинаков на обоих инаппах (поэтому reuse одинаково полезен для любого инаппа):

| Режим | navStart |
|---|--:|
| как сейчас (новый WebView каждый показ) | ~620–640 |
| прогрев (throwaway-инстанс) | ~375 |
| reuse, первый показ | ~275 |
| **reuse, показ №2+** (инстанс уже показывал контент) | **~61** |

`navFinish` (документ загружен) уже зависит от кэша: в тёплом стеке ~0.3 с (reuse, первый показ ~296 мс),
на показе №2+ ~146 мс — детали в profile.md.

**Ключевое (механизм):** «пол ~230 мс» на `loadHTMLString→navStart` — это цена **первого** реального
контент-навигейта. На инстансе, уже показавшем контент, следующий показ стартует навигацию мгновенно
(~4 мс) — что и видно в свежем прогоне выше (показ №2 navStart 52 мс). Отсюда дизайн: **один сессионный
тёплый cacher-вебвью**, а не отдельный прогрев на каждый инапп.

## Что шипим — фазы

| Фаза | Что | Стоит | Даёт | Риск |
|---|---|---|---|---|
| **1** | `.default()` (по версии iOS — изолированный стор) + прогрев/reuse одного инстанса | чистый SDK | основной выигрыш: ~3.4 с → ~0.5–0.8 с; reuse-инстанс до ~0.4 с | приватность `.default()` |
| **2** | Cacher грузит **настоящий index.html без formId** (актуальные версии, endpoint из конфига) | чистый SDK | первый холодный показ уже с прогретым рантаймом | 5-мин окно byendpoint |
| **3** (опц.) | Серверный `cacher.html` + префетч статичных картинок форм | фронт+бэк | покрывает картинки статичных форм | орг. работа с веб-командой |

Фаза 1 — минимальный шип, весь основной выигрыш. Фазы 2–3 — расширения.

## Возможности API вокруг WebView + кэш (iOS)

Точка входа — `WKWebViewConfiguration.websiteDataStore`, задаётся **при создании** WebView (потом не
поменять). Ниже — весь публичный API вокруг кэша/хранилища.

### Выбор хранилища

| API | Что | Переживает перезапуск |
|---|---|---|
| `WKWebsiteDataStore.default()` | общий персистентный стор апы | да |
| `WKWebsiteDataStore.nonPersistent()` | в памяти (private browsing) — **сейчас в SDK** | нет |
| `WKWebsiteDataStore(forIdentifier:)` iOS 17+ | изолированный стор по UUID (несколько, чище приватность) | да |
| `WKProcessPool` (на конфиге) | шарит web-content процесс/сессию между WebView | — |

### Что и чем кэшируется

- Веб-контент (скрипты/картинки/CSS) → **WebKit NetworkCache** (`Library/Caches/WebKit/…`), по
  HTTP-заголовкам CDN (см. TTL в overview §2). **Не** `NSURLCache`.
- `URLCache.shared` на веб-контент WebView **не влияет** — только на собственные `URLSession`-запросы
  SDK (фетч `index.html`).
- Типы данных (`WKWebsiteDataType`): DiskCache, MemoryCache, Cookies, Local/SessionStorage, IndexedDB,
  WebSQL, OfflineWebApplicationCache.

### Управление — что можем

| API | Что делает |
|---|---|
| `config.websiteDataStore = .default()` | включить персистентный кэш (рычаг №1) |
| `removeData(ofTypes:for:)` | удалить данные по origin |
| `removeData(ofTypes:modifiedSince:)` | удалить по дате (`.distantPast` = всё) — единственный реальный «подрезать кэш» |
| `remove(forIdentifier:)` iOS 17+ | снести весь изолированный стор |
| `fetchDataRecords(ofTypes:)` | список записей по origin (**без байт**) |
| `fetchAllDataStoreIdentifiers` iOS 17+ | список изолированных сторов |
| `httpCookieStore` | get/set/delete/observe куки |
| `isPersistent` | персистентный ли стор |

### Чего нет — не можем

- **Задать байтовый лимит кэша** — нет аналога `URLCache.diskCapacity`. Ёмкость системная, из свободного
  места на диске (десятки–сотни МБ; тир для голого WKWebView недокументирован).
- **Прочитать текущий размер в байтах** — `WKWebsiteDataRecord` байты не отдаёт (`dataSize` — SPI).
- **Запинить запись / гарантировать офлайн** — вытеснение вероятностное (LRU-подобное, по давлению
  ёмкости); HTTP-заголовки управляют свежестью/ревалидацией, но **не** защищают запись от вытеснения.

**Следствие:** бюджет держим политикой `removeData(modifiedSince:)` (по дате) или сносом изолированного
стора — не байтовым лимитом; на «всегда в кэше» не полагаемся (best-effort). Детали с цитатами — overview §6.

## Cacher: прогрев-страница — где живёт и что содержит

**Задача cacher.** Прогреть web-content процесс (первый `loadHTMLString` оплачивает спин-ап заранее) и
засеять общий рантайм в персистентный кэш (tracker.js + main.js + шрифты + byendpoint) — **без рендера
формы** (нет formId → показа нет). Опционально — предзагрузить статичные картинки форм.

### Три варианта, где живёт страница

| Вариант | Где | Версии ресурсов | Картинки форм | Работа |
|---|---|---|---|---|
| **A. Хардкод-строка в SDK** (прототип) | Swift `loadHTMLString` | хардкод `?v=` → рассинхрон после бампа | — | 0 (уже есть) |
| **B. Реальный `index.html` без formId** (реком. минимум) | существующий бутстрап на CDN | всегда актуальны | — | SDK-правка |
| **C. Серверный `cacher.html`** | бэк хостит | бэк шаблонит текущие | **да** | фронт/бэк |

### A — что в прототипе сейчас

Хардкод HTML-строкой, `loadHTMLString(cacherHTML, baseURL: "https://inapp.local/popup")`: `<script>` на
tracker/main (`?v=1.0.29`) + byendpoint (кэш-бастинг `floor(now/300)`, как рантайм) + `<link>` шрифты.
Минус: версии зашиты — после бампа рантайма cacher греет неактуальное (показу отдаётся свежее, но прогрев
впустую). Годится как измерительный прототип, не для прода.

### B — рекомендованный минимум (без бэка)

На прогреве SDK грузит не хардкод, а **существующий `index.html`** (тот же бутстрап, что у показа) с
`endpointId` из конфига, но **без formId**. Рантайм инициализируется, tracker тянет byendpoint (со своим
кэш-бастингом → URL совпадает с показом, без риска 5-мин границы), форма не рендерится. Версии всегда
актуальны (их диктует index.html). Единственное требование: **убедиться, что рантайм корректно без formId**
(не падает, просто ничего не показывает). Бэк/фронт — 0.

### C — серверный cacher.html (нужен ТОЛЬКО ради картинок)

Смысл варианта C — предзагрузить **статичные** картинки форм, чего B не делает. Ключ: **byendpoint
генерирует бэк, значит бэк знает все URL статичных картинок эндпоинта** — и может вписать их в cacher.html
как prefetch-ссылки. Рантайм-хуки для этого не нужны.

```html
<!-- GET https://<host>/cacher.html?endpoint=<endpointId> ; бэк шаблонит {{...}} -->
<!doctype html>
<html><head><meta charset="utf-8">
  <link rel="stylesheet" href="{{fontsCssUrl}}">
  <!-- общий рантайм ТЕКУЩИХ версий (бэк подставляет ?v=) -->
  <script src="{{mainJsUrl}}"></script>      <!-- .../content/main.js?v={{ver}} -->
  <script src="{{trackerJsUrl}}"></script>   <!-- api.mindbox.ru/scripts/v1/tracker.js?v={{ver}} -->
  <!-- byendpoint эндпоинта (тот же кэш-бастинг, что у показа) -->
  <script src="{{byendpointUrl}}"></script>
  <!-- статичные картинки форм — бэк перечисляет из byendpoint -->
  {{#each staticImageUrls}}<link rel="prefetch" href="{{this}}" as="image">{{/each}}
</head><body></body></html>
```

SDK грузит её в прогретый WebView (`loadHTMLString`/`load`), рендера нет. Тонкости:

- **Кэш-бастинг byendpoint:** если бэк ставит фиксированный `?_=`, возможен промах на 5-мин границе (URL
  cacher'а ≠ URL показа). Надёжнее — стабильный URL byendpoint на бэке (см. «Что решаем» п.5); тогда вопрос
  снимается совсем.
- **`<link rel="prefetch" as="image">`** кладёт картинку в кэш без рендера. Работает для **статичных** форм
  (URL зашиты в byendpoint, content-addressed, кэш 7 дней). **Рекомендательные** картинки (per-user)
  рождаются при рендере под юзера → заранее не перечислить, не префетчиваются.
- Cacher греет только общий рантайм + статичную статику; персональные данные не трогает.

### Что нужно от кого

- **A:** ничего (прототип).
- **B:** SDK — грузить `index.html` без formId + проверка «рантайм ок без formId». Бэк/фронт — 0.
- **C:** бэк — хостит `cacher.html`, шаблонит текущие версии, перечисляет статичные карт-URL из byendpoint.
  Фронт — 0 (если картинки вписывает бэк).

## Риски и ограничения

- Приватность `.default()` (cookies/localStorage) — разбор до прода (главный риск).
- Кэш best-effort: вытесняется по давлению ёмкости; офлайн не гарантирован (и не цель).
- Reuse держит `WKWebView` живым всю сессию — память (один инстанс, приемлемо).
- Прототипные метки и флаги — выкидные, удаляются; нужны тесты.

## Что исследовали и отклонили

Прежде чем прийти к «включить нативный кэш», проверили 3 способа заранее узнать полный список ресурсов
(это нужно было бы для офлайна / отдачи ресурсов руками):

| Подход | Вердикт |
|---|---|
| **1. Парсить выданный HTML** | ❌ Тупик: бутстрап 1.5 КБ, в нём 2 ссылки; рантайм-масса (byendpoint, картинки) не видна. |
| **2. Build-манифест** (фронт+билд+бэк) | ⚠️ Закроет статику шаблона, но рантайм-картинки (per-user) на билде не существуют. Дорого (L–XL). |
| **3. Наблюдать после показа** | ✅ Единственный видит рантайм-тяжёлое. На iOS «увидеть» — да; «отдать прозрачно силами SDK» — стена (кастомная схема не отдаёт скрипты; loopback переписывать нечего). Но **для скорости отдавать руками не нужно** — кэш по заголовкам держит нативный WebKit. |

**Вывод:** для **скорости** (не офлайна) строить ничего из этого не надо — весь выигрыш даёт нативный
кэш + прогрев/reuse. Полный офлайн (План Б) потребовал бы кооперации с веб-командой (индирекция
`resolveResourceUrl` в `popmechanic`/`tracker` + кэширующий прокси) — отдельная история, только если
появится требование офлайна.
