# WebView Memory POC

Стенд для оценки поведения нескольких встроенных `MindboxWebViewBlock` с реальными страницами:
порог вылетов по памяти, вид падения WebContent-процесса, эффект кэширования.

## Запуск

Экран открывается автоматически при запуске Example с launch-аргументами:

| Аргумент | Значение | Действие |
|---|---|---|
| `-webviewPOC` | — | Открыть POC-экран сразу, SDK Mindbox не инициализируется |
| `-webviewPOCCount` | `2` / `3` / `5` | Количество одновременных WebView-блоков |
| `-webviewPOCCache` | `YES` | Политика `returnCacheDataElseLoad` для всех загрузок (вкл. авто-reload после kill) |
| `-webviewPOCClearCache` | `YES` | Очистить кэш WebKit перед первой загрузкой (холодный старт) |

В Xcode: Edit Scheme → Run → Arguments Passed On Launch.

На экране: сегмент 2/3/5, свитч Cache, Reload all, Clear cache, балласт +200MB/Free
(грязная память в процессе приложения — для создания memory pressure на девайсе).

В шапке раз в секунду: footprint приложения (`task_vm_info.phys_footprint`),
`os_proc_available_memory` (запас до Jetsam-лимита приложения; на симуляторе всегда 0),
суммарные kills. На каждом блоке: состояние, число загрузок, kills, время последней загрузки.

Все события в консоли по маркеру `[POC]`.

## Замер памяти

Память страниц живёт в процессах `com.apple.WebKit.WebContent`, НЕ в приложении —
Xcode memory gauge и Allocations её не видят.

**Симулятор** (быстрая итерация; абсолютные цифры завышены — лимитов iOS нет):

```bash
ps -axo pid,rss,command | grep simruntime | grep WebKit.WebContent
footprint <pid>          # детальный footprint процесса
kill -9 <pid>            # детерминированная симуляция jetsam-kill
```

**Реальный девайс** (единственный источник правды по порогам):

1. Product → Profile → шаблон **Activity Monitor** (не Allocations), фильтр по `WebKit`.
   Колонка Memory по каждому `com.apple.WebKit.WebContent` — это и есть вес страницы.
2. Порог вылетов: жать «+200MB» до начала убийств WebContent (шапка покажет kills),
   фиксировать footprint приложения + суммарный вес WebContent в момент первого kill.
   Второй сценарий: свернуть приложение, открыть камеру/тяжёлые игры, вернуться.
3. Свидетельства системы: Настройки → Конфиденциальность и безопасность → Аналитика →
   Данные аналитики → файлы `JetsamEvent-*.ips` (какой процесс убит, rss, причина).
4. Вес контента изнутри страницы: `webView.isInspectable = true` (iOS 16.4+) →
   Safari → Develop → устройство → Timelines → Memory.

## Результаты реального устройства (2026-07-22, iPhone 16 Pro 8 ГБ / iOS 26.5.2)

Activity Monitor, All Processes, 39 с записи, 5 блоков, один «+200MB» балласта.
Трейс: `xcrun xctrace export --input <file>.trace --xpath
'/trace-toc/run[@number="1"]/data/table[@schema="sysmon-process"]'`
(footprint — 9-я size-in-bytes колонка в строке).

| Процесс | Пик footprint | Динамика |
|---|---|---|
| WebContent — самая тяжёлая страница | **697 МБ** | 87→697 МБ за ~6 с после загрузки, дальше плато |
| WebContent #2 | 176 МБ | стабильно |
| WebContent #3 | 167 МБ | стабильно |
| WebContent #4 | 121 МБ | стабильно |
| WebContent #5 | 111 МБ | стабильно |
| WebKit Networking (общий на приложение) | 109 МБ | |
| WebKit GPU (общий на приложение) | 78 МБ | |
| Example (само приложение) | 283 МБ | база ~80 МБ + 200 МБ балласта |

Итого 5 блоков ≈ **1.3 ГБ в WebKit-процессах**. Ещё 3 короткоживущих WebContent
по 20–30 МБ в первые секунды — служебные процессы site isolation, не jetsam.

Выводы:

1. **Порог вылетов на 8 ГБ устройстве не достигнут**: страница на 697 МБ прожила
   весь трейс, ни одного kill при суммарных ~1.7 ГБ. Фольклорные «300–450 МБ на
   WebContent» — про устройства с 3–4 ГБ RAM. Порог надо мерить на слабом железе
   (iPhone 11/12/SE) — там и живёт реальный риск.
2. **Профиль потребления подтверждён**: обычная страница 110–180 МБ, тяжёлая —
   700 МБ за 6 секунд. Один плохой лендинг ест больше четырёх нормальных страниц —
   без бюджета веса страницы для веб-стороны фича не полетит.
3. Приложению память страниц не приписывается: footprint Example стабилен
   (~80 МБ) независимо от блоков — вылет грозит WebContent-процессам, не приложению.

Следующий шаг: длинная запись (3–5 мин) с 8–10 нажатиями «+200MB» до роста
счётчика kills; затем тот же прогон на устройстве с 3–4 ГБ RAM. После сессии —
`JetsamEvent-*.ips` в Настройки → Аналитика (причина kill + rss).

## Ориентиры по устройствам

Apple лимиты не публикует — числа эмпирические (jetsam-плисты устройств, замеры
сообщества, форумы Apple) и зависят от версии iOS и текущего состояния системы.
Использовать как порядок величины, не как константы. Два разных лимита:
«лимит приложения» — сколько может занять сам процесс приложения до jetsam
(`os_proc_available_memory` показывает остаток); «потолок WebContent» —
практическая граница, после которой процесс страницы начинают убивать.

| Устройство (RAM) | Лимит приложения (~) | Потолок WebContent (~) |
|---|---|---|
| iPhone 7 / 8 / SE 1 (2 ГБ) | ~1.4 ГБ | 200–300 МБ |
| iPhone X / XR / SE 2–3 (3 ГБ) | ~1.4 ГБ | ~300 МБ |
| iPhone 11 / 12 / 13 mini (4 ГБ) | ~2.1 ГБ (ActiveHard 2098 МБ) | 350–450 МБ |
| iPhone 12–13 Pro / 14 / 15 (6 ГБ) | ~3–3.3 ГБ | ~450–600 МБ |
| iPhone 15 Pro / 16 / 16 Pro (8 ГБ) | ~4 ГБ | **>700 МБ — наш замер, kill не достигнут** |

Замечания:

- Потолки WebContent — наблюдения (Catch Metrics: iPhone 8/X ~300–400 МБ,
  iPhone 13/14 ~400–450 МБ; наш девайс-прогон: 697 МБ живёт на 16 Pro).
  Жёсткий верхний предел процесса — EXC_RESOURCE ActiveHard 2048 МБ (iPhone-класс),
  но практические убийства происходят сильно раньше из-за общего давления.
- Entitlement `com.apple.developer.kernel.increased-memory-limit` поднимает лимит
  только самого приложения (iPhone 13: ~2.1→~2.3 ГБ) и только на 6+ ГБ устройствах;
  на WebContent-процессы не влияет — для нашей фичи бесполезен.
- Практический вывод: продуктовый бюджет страницы должен исходить из худшего
  устройства парка (3 ГБ → ~300 МБ на процесс, т.е. страница со всеми ресурсами
  должна помещаться в ~150–200 МБ с запасом на пики рендера).

## Что уже известно с симулятора (2026-07-22, iPhone 17 / iOS 26.2)

- Каждый блок = свой WebContent-процесс; site isolation добавляет процессы под
  cross-origin iframe'ы (реклама): 2 блока (lenta+ozon) давали 8 WebContent-процессов.
- Реальные страницы тяжёлые: lenta/theverge раздувались до ~950–1070 МБ RSS на
  симуляторе (без лимитов iOS). На девайсе такие процессы будут убиты в районе
  ~300–450 МБ → регулярные перезагрузки блоков.
- `kill -9` WebContent: `webViewWebContentProcessDidTerminate` срабатывает, блок сам
  перезагружается; на время перезагрузки — белый прямоугольник (нужен снапшот-оверлей).
- Приложение при этом живёт: footprint самого Example стабильно ~60–70 МБ при любых
  манипуляциях с блоками.
- Эффект кэша (5 блоков, kill самого тяжёлого процесса, полный didFinish):

  | Метрика | Холодный кэш, default policy | Тёплый кэш + returnCacheDataElseLoad |
  |---|---|---|
  | Первая загрузка lenta.ru | 78 с | 2.1 с |
  | Первая загрузка theverge.com | 8.2 с | 8.0 с |
  | Перезагрузка после kill (theverge) | **134 с** | **4.8 с** |

  Вывод: авто-reload после kill без кэш-политики практически неюзабелен на тяжёлых
  страницах; `returnCacheDataElseLoad` сокращает восстановление в ~28 раз.
